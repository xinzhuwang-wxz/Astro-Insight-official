我建议把整个项目收束成一个主轴：**Crab Nebula 这片 Taurus/Crab 天区**，古代层讲“人类如何用图和文字组织天空”，现代层讲“人类如何用多波段和星表重建同一片天空”。这样你不会被“全宇宙叙事”拖散，且 SN 1054 的历史记录本来就和 Crab Nebula 的现代物理对应是同一条线。古代层的时间对齐不必做到全精确复原，catalog 层再用 Astropy 做 epoch 和 proper motion 传播即可；`SkyCoord.apply_space_motion()` 就是为这类跨时间位置更新准备的。HSC v3.1 的 proper motion 主要只在 SWEEPS 视场通过 CasJobs/API 提供，Crab 主线里不必强行纳入。([Lehigh University][1])

先说你最少还要补什么数据。古代层建议补两张小表就够：一张是“SN 1054 记录点表”，字段放 `date`、`source`、`translated_note`、`position_note`、`brightness_estimate`、`uncertainty`；另一张是“星官锚点表”，字段放 `asterism_name`、`hip_id`、`weight`、`note`。现代层不需要再加很多东西，你现有的 Gaia、HSC、Chandra 已经足够。你如果想做更稳的可视化，优先用你已经有的 `caafrc`、`clean_cols_GaiaDR3Crab`、`clean_cols_HSCv3.1Crab`、`crab0.3-10keV.fits`，再把 SN 1054 的 PDF 当作历史文本来源。([チャンドラ宇宙望遠鏡][2])

技术栈我建议分成四层。数据层用 Python、pandas、numpy、Astropy、astroquery、astropy.io.fits、pdfplumber；存储层用 Parquet/CSV/FITS 做原始缓存，PostgreSQL 保存整理后的 catalog 和 cross-match 结果；后端用 FastAPI + Uvicorn 暴露查询接口；前端用 React + TypeScript + Vite，图表用 ECharts 和 Plotly，星图/网络图用 D3，3D 用 Three.js，HiPS 视图用一个支持 HiPS 的 viewer。HiPS 这个标准本身就是为“分层切片、渐进加载、无缝缩放和平移”设计的，所以非常适合你的天区浏览器。([IVOA][3])

下面按你的每一种可视化拆开。

一，星图连线。
你要做的不是“复原完整古图”，而是“把古代连线方式和现代星表对应起来”。先从 `caafrc` 里选 Taurus/Crab 周边的 HIP 星，利用 RA、Dec、Vmag、pmRA、pmDE、Plx、RV 生成一个可传播的参考星集；再用 Astropy 把它们统一到同一历元，绘制成 sky map；最后把你手工整理的星官锚点连线叠上去。前端用 D3 画线，用 SVG 或 Canvas 叠在 sky projection 上，底图可用 Mollweide 或 Aitoff。这里的重点结论不是“古图是否精确”，而是“古人如何通过连线把天空做成可读结构”。([Astropy][4])

二，亮度分层。
这部分最适合做成一个“从稀疏到密集”的视觉层级。先把 `Vmag` 或 `G magnitude` 分成几档，例如亮星、中亮、暗星；再用大小、透明度、发光圈层做编码，叠在同一张天图上。古代层可以用 SN 1054 文本里的亮度描述作为叙事节点，现代层可以用 Gaia/HSC 的测光值作为稳定的数值基础。这里建议用 Python 先做分箱和颜色映射，前端用 ECharts/Plotly/Canvas 渲染，图例一定要做成可切换，因为这张图本质上是在讲“人眼如何在天空里先看到什么、后看到什么”。SN 1054 的历史记录本来就可以重建一条近似光变曲线。([Klaipėdos Universitetas][5])

三，dive in 光变曲线。
这条线最好做成“历史记录时间轴”，而不是严格天文测光曲线。你需要从 SN 1054 的 PDF 里人工抽取几个关键记录点：出现时间、白昼可见期、夜间可见期、逐渐消失的时间，再把这些点整理成一条带不确定性的估计曲线。实现上可以先把日期转成统一时间轴，哪怕先用相对天数，再做纵轴亮度估计；前端用 Plotly 时间序列或 ECharts timeline，加注释卡片显示原文摘录。这个模块的结论应该写成“古代记录如何把一次超新星事件变成可读的时序信息”。([Klaipėdos Universitetas][5])

四，多分辨率金字塔 HiPS。
这一项是你现代平台的“总入口”。HiPS 标准本身就定义了按层级切片、逐级细化的天空数据组织方式，天然支持 progressive zooming 和 panning，所以特别适合做一个“从全局到局部”的浏览器。实现上，你不必自己从零造一个全天天区金字塔；更实用的做法是用现成的 HiPS 资源或把你这片 Crab/Taurus 视场做成自己的 tile pyramid，然后在前端做缩放与按层加载。后台返回不同缩放级别的 catalog 点集、HSC cutout、Chandra X-ray 图层，前端用 HiPS viewer 叠加点位和选区。这个模块的结论是：**同一片天空在不同分辨率下会暴露不同结构**。([IVOA][3])

五，高维数据降维。
这项最适合把 Gaia 和 HSC 的表格值“变成结构”。你可以把 Gaia Crab 表里的 `parallax`、`pmra`、`pmdec`、`phot_g_mean_mag`、`phot_bp_mean_mag`、`phot_rp_mean_mag`、`bp_rp`、`bp_g`、`g_rp`、`ruwe`、`teff_gspphot`、`logg_gspphot`、`mh_gspphot` 等字段做标准化，再配合 HSC 的多滤镜 `Magnitude`/`Magnitude error` 构造特征矩阵；先用 PCA 做可解释投影，再用 UMAP 或 t-SNE 做局部结构展示。Gaia 官方的可视化服务本来就提供 histograms、scatter plots、binned plots、sky maps、CMD 和 HRD，所以你的前端就应该遵循这套语法：先总体分布，再局部结构，再交互筛选。结论重点放在“哪些变量最能区分恒星/星系/异常源”。([宇宙欧洲航天局][6])

六，三维空间与 VR。
这项我建议降级为“展示层”而不是主任务。你可以用 Gaia 的视差把近邻恒星投到三维空间里，显示距离、速度向量和局部密度；但在 Crab 这块视场里，不要把 HSC 也硬塞进运动学，因为 HSC v3.1 的 proper motion 主要只在 SWEEPS 视场提供，Crab 区域里它更适合做光度源表和影像叠加。实现上，先把 Gaia/HIP 转成笛卡尔坐标，再用 Three.js 或 Plotly 3D 做可旋转点云；如果想更进一步，再加 WebXR 只是演示性质。结论应该是“近邻恒星的三维分布和二维天空图并不等价”。([MAST][7])

七，多波段融合。
这是你最能出效果的一项。用 Chandra 的 Crab 0.3–10 keV FITS 做 X-ray 底图，再叠 HSC 的多滤镜成像和 Gaia/HIP 的点源层。HLA 的交互显示明确支持源表叠加和天体测量偏移修正，这对你做多波段融合非常有启发：先做 WCS 对齐，再做图层切换，再做透明度叠加。实现上用 `astropy.io.fits` 读 X-ray 图，用 `astropy.wcs` 对齐坐标，用 `reproject` 或等价方案统一投影，前端做波段开关和透明度滑块。这个模块最重要的结论是：**同一对象在不同波段下显露的是不同物理过程**。([チャンドラ宇宙望遠鏡][2])

八，CMD 和 HRD。
这是你必须做的核心图之一。Gaia 官方的可视化服务本来就把 CMD 和 HRD 作为标准视图；HSC 侧也有明确的 color-magnitude diagram 例子，可以直接用 CasJobs 或 API 去做。你这里要注意一点：HSC 和 Gaia 的滤光系统不同，别硬把它们混成一张物理图，最稳的是做并排图，或者各自一套 CMD，再通过选区联动。技术上先从 Gaia 的 `phot_g_mean_mag`、`phot_bp_mean_mag`、`phot_rp_mean_mag` 算颜色和绝对星等；HSC 用不同滤镜组合做伪颜色或局部 CMD。结论可以讲到“不同演化阶段在颜色—亮度平面上的分离”。([宇宙欧洲航天局][6])

九，自行与径向速度。
这项主要属于 Gaia/HIP。你可以把 `pmra`、`pmdec`、`radial_velocity` 做成天球投影上的箭头和速度场，再把速度大小映射到颜色或长度。对 HIP 数据，Astropy 的 `apply_space_motion()` 可以把同一批星在不同历元的位置传播出来，所以你可以做一个“时间滑块”，让箭头或位置随 epoch 变化。HSC 在 Crab/Taurus 主线里不承担这一模块，因为它没有你需要的通用运动学列。结论是“天空上的点不只是点，它们会移动，而且运动方向本身就是结构信息”。([Astropy][4])

十，光谱可视化。
这项适合做成“点开即看”的第二层信息。你的 Gaia 表里已经有 `has_xp_continuous`、`has_xp_sampled`、`has_rvs` 这些 flags，所以可以先把有光谱的源筛出来，再做一条 1D 光谱视图和 CMD 联动；HSC 本身主要是多波段成像，不是光谱星表，所以不要强求把它当光谱源。前端用 Plotly 或 ECharts 画谱线，后台用 flag 控制是否显示光谱面板。结论是“颜色空间和光谱空间互相验证，能增强分类可信度”。([MAST][8])

十一，联合巡天交叉可视化。
这是你平台最像“系统”的地方。Gaia 可以通过 ADQL 查询，HSC 可以通过 CasJobs/API 或 HLA 的 catalog overlay 接入，Chandra 则提供 FITS 图层；你先做交叉匹配，再在前端同时展示匹配源、未匹配源、图像 cutout 和属性关联散点。HLA 交互显示本身就支持 HSC overlay 和 astrometric shift correction，这意味着你的联动视图是有现成交互范式的。这里的关键结论通常是“哪些源跨 catalog 一致，哪些源是拥挤区、分辨率差异或异常对象”。([宇宙欧洲航天局][9])

十二，多视图联动。
这不是单独一个图，而是你平台成败的关键。做法很简单：所有视图共享一个 selection state，点击天空图里的一个对象，右侧自动更新 CMD、光谱、历史记录卡片、光变曲线和对应影像 cutout；在 CMD 里框选一簇点，天空图和表格同步高亮。前端可以用 React 状态管理加事件分发，图表层用 ECharts 的 `dispatchAction`、Plotly 的 selection events、D3 的 brush/zoom。HLA 的交互显示已经说明“catalog overlay + 图像缩放 + 窗口内读数”这件事是自然且必要的，所以你做联动会很顺。([Hubble Legacy Archive][10])

十三，AI 辅助可视化。
这项只建议做成最后的可选层，不要让它抢主线。你可以用预训练 CNN 对 HSC 图像 cutout 做星系形态初分、致密源自动标注，或者把 Gaia 的物理参数作为辅助标签去解释图像分类。技术栈就是 PyTorch + torchvision 或类似 CV 预训练模型。这个模块的意义主要是“减少手工标注”和“给视觉叙事加一个智能注释层”，不建议把它做成核心研究点。([MAST][8])

如果你只想做一个两学分里最稳、最像作品集的版本，我建议把优先级压成这样：先做星图连线、亮度分层、历史光变曲线、HiPS 视图、CMD/HRD、交叉匹配和多视图联动；把三维、光谱和 AI 作为加分项。这样你既保住了“古今天空结构”的叙事，又不会把工程量推到失控。你后面如果要，我可以继续把这套方案拆成数据库表结构和后端接口清单，直接进入开发。
